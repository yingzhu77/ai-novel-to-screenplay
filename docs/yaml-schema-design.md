# 剧本 YAML Schema 设计文档

> 七牛云 × XEngineer 暑期实训营 — AI 小说转剧本工具

---

## 一、设计哲学：三个来源的融合

本 Schema 的设计不是凭空定义的，而是融合了三个来源：

| 来源 | 吸收了什么 | 对应方案 |
|------|-----------|----------|
| 好莱坞标准剧本格式（Final Draft） | 场景头(scene_heading)、舞台指示(action)、专业命名 | 方案 A |
| AI 能力边界 | 只定义 AI 能可靠提取的字段，避免幻觉输出 | 方案 B |
| 实体-关系数据建模 | 角色作为全局独立实体，跨章节统一识别 | 方案 C |

**设计原则：AI 负责提取内容，Schema 负责保证结构。AI 能做到的才定义，做不到的不强行要求。**

## 二、为什么选 YAML 而不是 JSON？

### 2.1 可读性

```yaml
# YAML：层级关系一目了然
dialogues:
  - speaker: 李明
    text: "你迟到了。"
    emotion: 不满
    subtext: 我等了半小时，不是在闹着玩
```

```json
// JSON：嵌套深了很难阅读和编辑
{ "dialogues": [{ "speaker": "李明", "text": "你迟到了。", "emotion": "不满" }] }
```

### 2.2 注释支持

编剧拿到剧本后需要标注修改意见。YAML 的 `#` 注释天然支持，JSON 不支持。

### 2.3 行业贴近性

剧本行业标准格式（Final Draft）本身就是层级化结构：剧本 → 幕 → 场 → 对话。YAML 的缩进层级完美匹配这个结构，而 JSON 的大括号嵌套不符合编剧的阅读习惯。

### 2.4 为什么同时支持 JSON 导出？

实际开发中 JSON 更易于前端解析和渲染。工具默认输出 YAML 给编剧编辑，JSON 给前端展示。两种格式从同一 Schema 派生，结构完全一致。

## 三、分层结构设计

```
Screenplay（剧本）
├── meta              ← 元数据层：谁写的、改编自哪、版本号
├── characters[]      ← 角色实体层：全局唯一，跨章节去重
└── chapters[]        ← 内容层：按章节组织
    └── scenes[]      ←   场景层：每个场景独立
        └── dialogues[] ←     对话层：对白序列
```

### 3.1 为什么角色是全局实体而不是嵌套在章节里？

一个角色可能在多个章节出现。如果把角色信息嵌入每个章节，会导致：

1. **重复**："李明"在每章都有 `traits`，冗余
2. **不一致**：第一章描述李明"性格急躁"，第三章 AI 可能产出"性格温和"
3. **无法跨章节查询**：无法回答"这个角色在哪些章节出场"

将角色提升为全局实体，用 `characters_present` 引用名称，解决了以上所有问题。这是方案 C 的核心贡献。

### 3.2 为什么按章节组织而不是按"幕"？

小说天然以章节为单元，AI 逐章处理。如果强行按剧本的"幕/场"组织，需要 AI 理解剧情推进和冲突升级——这超出了当前 AI 在 3 天开发周期内的可靠能力。按章节组织是 AI 能力边界内最自然的映射。

## 四、核心字段设计决策

### 4.1 `scene_heading`：为什么用标准格式？

```
"INT. 蓝山咖啡厅 - 下午"
```

好莱坞剧本标准格式是 `INT./EXT. 地点 - 时间`。采用这个格式有两个原因：

1. 让输出物像"真的剧本"，体现行业理解
2. 结构化信息从字符串中可提取：`INT.` = 室内，`蓝山咖啡厅` = 地点，`下午` = 时间

如果 AI 无法判断室内/室外，`scene_heading` 可以降级为 `"蓝山咖啡厅 - 下午"`，`location` 和 `time` 字段独立兜底。

### 4.2 `emotion` 和 `subtext`：为什么是可选的？

```
dialogue:
  speaker: 李明
  text: "随便吧。"
  emotion: 冷漠          # AI 从上下文推断
  subtext: 我不想继续这个话题  # AI 从上下文推断
```

`emotion` 和 `subtext` 是"AI 能力边界"的典型例子：

- **能做**：如果原文有明确的情绪描写（"他冷冷地说"），AI 可以可靠提取
- **不能保证**：如果原文没有线索，强行要求 AI 输出会引入幻觉

因此这两个字段标注为 `optional`：有线索就填，没有就留空，不做强制。这体现了方案 B 的务实思维。

### 4.3 `action` 字段的双重角色

`action` 字段在场景层级是**场景描写**（叙述转舞台指示），在对话层级是**动作注解**（角色的伴随动作）：

```yaml
scene:
  action: "李明推开咖啡厅的玻璃门，风铃响起。他环顾四周，目光落在角落的卡座上。"
  
  dialogue:
    speaker: 李明
    text: "你迟到了。"
    action: "拉开椅子坐下，没有看对方"  # ← 伴随动作，非场景动作
```

这是设计上的有意重合：两者本质上都是"将小说叙述转化为可视化的舞台指示"，只是粒度不同。统一命名为 `action` 而非区分 `scene_action` 和 `dialogue_action`，降低 Schema 复杂度。

### 4.4 `aliases`：角色别名映射

```yaml
character:
  name: 李明
  aliases: [小李, 明哥, 李总]
```

小说中同一角色常有多个称呼。`aliases` 是跨章节角色去重的关键——AI 通过别名识别"小李"和"李明"是同一个人，而非创建两个角色实体。

### 4.5 `subtext`：潜台词

这是本 Schema 的一个创新点。剧本的魅力在于"角色说的 ≠ 角色想的"。`subtext` 让 AI 尝试提取对话的潜台词：

```
对话原文："好啊。"（角色其实不愿意）
→ text: "好啊。"
→ emotion: 强颜欢笑
→ subtext: 我其实不愿意，但不想争执
```

这个字段是 AI 能力的前沿，不一定每次都能准确提取，但定义这个字段本身展示了设计者对角本创作本质的理解。

## 五、Schema 的可扩展性

当前 Schema 为本次 3 天开发的最小可用版本。预留了未来扩展空间：

| 扩展方向 | 实现方式 | 当前不做原因 |
|----------|----------|-------------|
| 多幕结构 | 在 chapters 之上加 `acts[]` | 小说无"幕"概念 |
| 转场指示 | 在 Scene 中加 `transition: CUT TO/FADE IN` | AI 提取准确率低 |
| 分镜标注 | 在 Scene 中加 `shots[]` | 超出 AI 能力 |
| 多版本对比 | `draft_version` 字段已预留 | 多版本管理是独立功能 |
| 协作批注 | 在各级加 `comments[]` | 需要用户系统和后端 |

## 六、设计决策速查表

| 决策 | 方案 | 为什么 |
|------|------|--------|
| 数据格式 | YAML（主）+ JSON（辅） | YAML 可读可注释，JSON 便于前端 |
| 角色模型 | 全局实体 + 名称引用 | 避免跨章节重复和不一致 |
| 组织结构 | 按章节（非按幕） | 匹配 AI 逐章处理的能力边界 |
| emotion/subtext | 可选，不强制 | AI 有线索就提取，没有不编造 |
| scene_heading | 标准格式 + 独立字段兜底 | 行业规范 + 结构化保障 |
| 潜台词(subtext) | 定义但可选 | 展示对角本创作本质的理解 |
| 章节拆分 | 正则 + AI 辅助 | 纯文本处理更快，AI 只做兜底 |
